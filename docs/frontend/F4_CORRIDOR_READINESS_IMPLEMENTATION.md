# F4 Corridor Planning & Operator/Device Readiness Frontend

## Purpose

F4 surfaces the existing E7 Corridor Planning and E8 Operator & Device Readiness read models in the governed Wishland / Enawuga frontend. It does not add a new planning algorithm, training authority, device-control plane or geographic approval mechanism.

## Wishland / Enawuga design continuity

F4 uses the canonical design system in `WISHLAND_BRAND_AND_DESIGN_SYSTEM.md`: the official Wishland navy/teal/gold palette, Geist application typography, low-shadow bordered surfaces, semantic status labels and explicit Stage-4 authority boundaries. The official Wishland wordmark and mark are imported from `abeselomchernet/wishland` and the former temporary sprout-only corporate treatment is retired. Wishland remains the technology provider; Enawuga remains the product/platform identity.

## Corridor Planning UX

Route: `/hub/corridor-planning`. The page consumes `/api/demo/hubs/:hubId/corridor-planning` through the typed Hub client. Candidate cards expose synthetic readiness, evidence completeness, connectivity/logistics/liquidity profiles, missing evidence and recommendation state. F4 intentionally does not add a conventional map, exact coordinates, real partner commitments or real demand/connectivity/logistics/liquidity/cost claims.

The UI preserves the backend distinction between recommendation and authority: a recommendation is not authorization. `RECOMMEND_BOUNDED_REVIEW` is review support only. Geographic authorization, pilot authorization, expansion authorization and live-site activation remain false. The planning digest is shown only as an integrity reference and does not prove evidence truth or external acceptance.

## Operator & Device Readiness UX

Route: `/hub/readiness`. The page consumes `/api/demo/hubs/:hubId/operator-device-readiness`. It shows synthetic training completion, certification/refresher state, operational readiness, device posture, support evidence and return-to-service review state.

The page does not display real operator identity, real telemetry or a live support-system integration. It contains no Activate Device, Approve Operator, Remote Command, Firmware Update or automatic return-to-service control. Readiness/certification does not create financial, provider, settlement or regulated authority.

## Role boundary

The F4 links are added only to management-role navigation generated by `WorkspaceManifest`. Agent navigation remains bounded. Navigation is presentation convenience only; the server remains authoritative for route/API access.

## Evidence UX

Both pages reuse `EvidenceDrawer` and `GovernedStatus`. Evidence drawers show server-provided references, schema version, digest/integrity reference, limitation and authority implication. Missing evidence remains missing/unknown; it is never fabricated as PASS.

## Stage-4 non-claims

F4 is synthetic decision-support only. It adds no real geographic authorization, real pilot, external evidence acceptance, real identities, real device telemetry, remote device control, live provider connectivity, real funds, PartnerFI posting/settlement or production authority.
